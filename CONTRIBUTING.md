# Contributing to Pragmatic-Ts

Start with the repository README, AGENTS.md and PROJECT.md. For the company foundation, also read the [engineering constitution](https://github.com/Pragmatic-Ts/.github/blob/main/docs/ENGINEERING_CONSTITUTION.md).

Propose a focused change tied to an agreed problem. Use a short-lived branch and a pull request describing user-visible behavior, rationale, validation and risks. No mandatory ticket system, branch prefix or commit-message format is imposed across all products.

For bugs, include a minimal reproduction and sanitized environment details. For features, explain users, problem evidence, scope, alternatives and acceptance criteria. Keep credentials and customer data out of issues, logs and attachments.

Run the documented checks on the final revision. Add meaningful tests for risk and behavior. State what ran, failed, was skipped or still needs live acceptance. Keep setup, architecture and implementation ledgers accurate.

Review correctness, ownership boundaries, failure handling, security, readability, tests and release implications. Do not weaken checks to pass CI. Resolve review findings before release.

Product repositories define their own contribution commands and deployment authority. Organization defaults do not automatically impose product requirements. Public visibility alone does not grant a license; consult that repository's license and obtain permission when needed.

Security issues follow [SECURITY.md](https://github.com/Pragmatic-Ts/.github/blob/main/SECURITY.md), not public bug reports.
